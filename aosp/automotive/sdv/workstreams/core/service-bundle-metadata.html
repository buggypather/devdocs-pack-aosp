Service bundle metadata

This page explains how to use the mandatory and optional service bundle metadata fields.

Mandatory metadata

The service bundle execution model requires each service bundle to define the following metadata:

  • Name of the service according to the SDV naming convention
  • Integer and string representation of the service bundle version
  • Path to the service bundle library 
sdv_service_bundle_metadata {
  # Name of the service bundle.
  #
  # Must follow SDV service naming convention rules.
  # Ref: https:/automotive/sdv/core-areas/naming-conventions
  #
  # When using VSIDL catalog and middleware generation, this name must be
  # equal to the service bundle name defined in the catalog.
  name: "TheNameOfTheServiceBundle"

  # Service Bundle Version Number.
  # Must be non-negative number.
  version_number: 1

  # Service Bundle Version Name.
  # Must be non-empty string.
  version_name: "1.0 alpha"

  # Path to the native library to be loaded as service bundle.
  # Must be the relative path from the APEX root directory
  native_library_path: "lib64/libservice_bundle.so"
}
Tip: You can add several service bundles in one manifest file, if they are to be stored in the same package.
# Service bundle one.
sdv_service_bundle_metadata {
  name: "ServiceBundleOne"
  ...
}
# Service bundle two.
sdv_service_bundle_metadata {
  name: "ServiceBundleTwo"
  ...
}

Optional metadata

Optional metadata support specific SDV capabilities.

Orchestration metadata

The SDV orchestration configuration provides a mechanism for controlling service bundles startup and shutdown behavior. The SDV orchestration configuration defines a set of rules that determine when and how actions are performed on service bundle instances. These rules are based on vehicle, power and custom modes.

To associate an orchestration configuration to the service bundle, provide the path to the prebuilt_etc module in the optional orchestration_config_path field:

sdv_service_bundle_metadata {
  ...
  # Path to the orchestration config file.
  # Warning: Shall be relative path to the APEX root directory.
  orchestration_config_path: "etc/configuration/orchestration/configuration.textproto"
}

Authorization policy path

The SDV authorization policy provides a mechanism for declaring permissions for the service bundle. The authorization policy defines what actions the service bundle can perform (such as publish, subscribe, serve, or call).

To associate an authorization policy to the service bundle, provide the path to the prebuilt_etc module in the optional authorization_policy_path field:

sdv_service_bundle_metadata {
  ...
  # Path to the authorization policy file.
  # Warning: Shall be relative path to the APEX root directory.
  authorization_policy_path: "etc/authz/permissions.textproto"
}

VSIDL provider metadata

The VSIDL provider metadata is a part of a mechanism for integrating service bundles with Diagnostics and SOME/IP platforms agents.

To associate a VSIDL provider metadata with a service bundle, provide the path to the prebuilt_etc files that contain generated metadata files in the optional vsidl_schemas_path / diagnostics_config_path / (SOME/IP config APEX only) external_service_bundle_metadata_path field:

sdv_service_bundle_metadata {
  ...
  # Path to the file with protobuf schemas extracted from bundle's VSIDL definition.
  # Warning: Must be relative path to the APEX root directory.
  vsidl_schemas_path: "etc/vsidl_provider/TheNameOfTheServiceBundle-vsidl-config.binpb"

  # Path to the diagnostics config file.
  # Warning: Shall be relative path to the APEX root directory.
  diagnostics_config_path: "etc/vsidl_provider/TheNameOfTheServiceBundle-diag-config.binpb"

  # Path to the SOME/IP config file. To be used in SOME/IP configuration apex only.
  # Warning: Must be relative path to the APEX root directory.
  external_protocol_mapping_path: "etc/vsidl_provider/someip-config.binpb"
}

To learn more, see VSIDL Provider Overview.

Log tag metadata

The log tag attribute specifies the unique identifier for logs generated by the service bundle. If this attribute is not defined, a default tag is automatically generated using the package name, service bundle name, and instance name. For optimal clarity, define a concise and unique log tag.

Custom metadata

Custom metadata allows OEM and vendors to define some specific service bundle metadata

sdv_service_bundle_metadata {
  ...
  # Custom service bundle metadata map.
  # Key is a string, value is a string.
  #
  # 1st custom metadata value.
  custom_metadata {
    key: "question"
    value: "Answer to the Ultimate Question of Life, the Universe, and Everything"
  }
  # 2nd custom metadata value.
  custom_metadata {
    key: "answer" value: "42"
  }
}
Caution: The entire size of all custom metadata fields should be limited to 10 KB. This is a soft limit, which comes from the binder buffer limit. This can lead to a binder transaction failure and the metadata from entire service bundles becomes unavailable.
Tip: To reduce the size of the custom metadata field extract all the related metadata in a separate file, create a prebuilt_etc module with this file and reference the path to this file in the custom metadata.
sdv_service_bundle_metadata {
  ...
  # Custom metadata values are stored in etc/.
  custom_metadata {
    key: "path_to_custom_metadata"
    value: "etc/configuration/file"
  }
}

Full example

# proto-file: //system/software_defined_vehicle/core_services/service_bundles_registry/proto/sdv_service_bundles_manifest.proto
# proto-message: SdvServiceBundleManifestEntry

# SDV service bundle.
sdv_service_bundle_metadata {
  # Name of the service bundle.
  # Must follow SDV service naming convention rules.
  name: "TheNameOfTheServiceBundle"

  # Service Bundle Version Number.
  # Must be non-negative number.
  version_number: 42

  # Service Bundle Version Name.
  # Must be non-empty string.
  version_name: "42.0.beta"

  # Path to the native library to be loaded as service bundle.
  # Must be the relative path from the APEX root directory.
  native_library_path: "lib64/libservice_bundle.so"

  # The log tag used for Android logging for the service bundle.
  # If not specified, a tag derived from service bundle FQIN will be used.
  log_tag: "current_service_bundle"

  # Path to the orchestration config file.
  # Warning: Shall be relative path to the APEX root directory.
  orchestration_config_path: "etc/configuration/orchestration/configuration.textproto"

  # Path to the file with protobuf schemas extracted from bundle's VSIDL definition.
  # Warning: Must be relative path to the APEX root directory.
  vsidl_schemas_path: "etc/vsidl_provider/TheNameOfTheServiceBundle-vsidl-config.binpb"

  # Path to the diagnostics config file.
  # Warning: Must be relative path to the APEX root directory.
  diagnostics_config_path: "etc/vsidl_provider/TheNameOfTheServiceBundle-diag-config.binpb"

  # Path to the SOME/IP config file. To be used in SOME/IP configuration apex only.
  # Warning: Must be relative path to the APEX root directory.
  external_protocol_mapping_path: "etc/vsidl_provider/someip-config.binpb"

  # Custom service bundle metadata string.
  # Key is a string, value is a string.
  custom_metadata {
    key: "key" value: "value"
  }

  # Custom metadata values are stored in etc/.
  custom_metadata {
    key: "path_to_custom_metadata"
    value: "etc/configuration/file"
  }
}
